实时 KWS 事件
不止床号

在实时对话的音频流里挑出会改变业务状态的关键词：床号、病区、下一床、暂停记录、查体段落…… 服务端只记住“说出口的值”并标到转写上，需要业务知识的判断交给业务端，业务端随时可以纠正。

01

三方分工：谁处理什么

点一个情形，看 KWS 引擎、服务端上下文、业务端各自做了什么。原则：服务端不猜业务，只处理显式说出的槽位值；需要查房队列、权限、确认流程的语义归业务端。

KWS ENGINE

KWS 引擎

sherpa-onnx 声学关键词检测，按收包顺序在独立推理阶段运行。只认关键词表里的词，不转写、不解释。
→
SERVER CONTEXT

服务端上下文

按音频时间记录上下文槽位（默认 bed）的变化，给转写片段打 context 标签。
⇄
BUSINESS CLIENT

业务端

解释指令和标记，持有查房队列与 UI；需要改上下文时发 set_context。
02

关键词表：标签就是协议

每个关键词带一个 @类别:值 标签，命中时原样返回。类别是否在 KWS_CONTEXT_SLOTS 里，决定它是“上下文槽位”还是“只推事件”。改改左边，看右边怎么变。

格式：关键词 [:增益] [#阈值] @类别:值。拼音为演示用小字典，以 scripts/build_kws_keywords.py + 模型 tokens.txt 为准。

四种消息

06

部署与验证现状

KWS 默认关闭。KWS_ENABLED=1 时配置必须完整、模型必须能加载，否则服务启动失败，不静默降级。

已验证

  • zh-en-3M（2025-12-20）与 wenetspeech-3.3M 均检出“十二床”“十五床”“下一床”“体温”（macOS TTS 合成音频）
  • 检测延迟约 0.5–0.9s；单 CPU 线程 RTF 约 0.006
  • 该样本上“二床/十二床”“一床/下一床”无互相误触发
  • 接入服务后的时间轴、context 标注、配置缺失启动失败
  • 回归测试覆盖：槽位/事件分流、片段中途切换、set_context 校验、晚到命中、KWS 故障、只录音

未验证

  • 真实病房语音的召回与误触发（TTS 样本不能代表）
  • “暂停记录”在 TTS 样本上未检出，需真实录音调 :增益 / #阈值
  • 多会话共享单线程 kws 阶段的负载：压测看 /v1/live/metrics 的 kws wait_ms；估算约 160 路实时并发前不会积压

模型与依赖

  • 推荐 sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20（中英混合，约 3M 参数）
  • 备选 wenetspeech-3.3M-2024-01-01
  • sherpa-onnx>=2.0.1；生成关键词表另需 pypinyin
  • sherpa-onnx 不输出置信度，误触发靠逐词阈值与 2s 去重
