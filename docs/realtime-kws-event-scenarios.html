04

两种方案，怎么选

已经在模拟器里试过两种场景了，这是它们各自的边界、收益和代价。

SCENARIO A

只输出 KWS 事件

业务端只需实时知道床号或控制指令，不需要正文。

典型用例

  • 说"12床"→ 前端切到 12床病人页
  • 说"下一床"→ 按队列切到下一位
  • 说"开始记录 / 暂停记录"→ 控制录音状态
  • 正文由其他系统处理，KWS 只打状态点

优点

  • 改动最小，业务边界清楚
  • 不要求业务端处理转写文本
  • 适合先验证识别可靠性
  • KWS 失败不影响主转写链路

限制

  • 无法直接生成查房正文
  • 只解决"切状态"，不解决"说了什么"
  • 正文归属仍需 ASR 配合
SCENARIO B

KWS + ASR 完整事件流

业务端需要实时正文，并希望系统自动把内容归属到当前床号。

典型用例

  • "12床，今天体温正常"→ 实时显示到 12床
  • "15床，昨晚咳嗽加重"→ 自动切换并追加
  • 边查房边校对、修正文本

优点

  • 支持实时查房记录生成
  • 前端可以边听边显示边改
  • 床号切换和正文归属都可追溯
  • 适合完整 AI 助理产品形态

限制

  • 业务端需处理 partial / final / 状态切换
  • ASR 延迟和错误依然存在
  • 需处理 KWS 与 ASR 的时间边界

06

怎么把事件送到业务端

实时音频上传 + 事件下行，首选 WebSocket。其他方式适合不同的解耦程度。

WebSocket

同一条全双工连接里：客户端上推音频帧，服务端下推 kws.detected / state.changed / asr.partial / asr.final。延迟最低，最适合实时场景。

什么时候用前端实时上传音频并接收事件，业务直接由前端驱动。

Server-Sent Events

服务端单向下推事件流。音频从别的通道（HTTP 上传 / RTP 流 / 第三方系统）进入，业务系统只接收结果。简单可靠，浏览器原生支持。

什么时候用音频不通过同一连接上传，业务只关心结果事件。

07

该选哪个？

回答两个问题，给你一个推荐方案。

业务端需要实时拿到医生说的正文吗？
"正文"指的是医生这一句话原原本本的转写内容，不只是"切到 12床"这种状态。
已有的 ASR 主链路允许被影响吗？
如果新 KWS 模块挂了，会不会影响原本的会议转写？
能接受业务端处理 partial / final 吗？
需要前端区分临时转写和最终转写、按床号归属、支持人工修正。
推荐方案

场景 A：只输出 KWS 事件

第一版用最小改动验证实时床号识别是否有业务价值。事件 = kws.detected + state.changed，业务端简单消费。

通信选 WebSocket，前端直接上音频、收事件。

推荐方案

场景 A + 旁路部署

主转写链路保持不变。KWS 作为旁路服务，通过消息队列发事件给业务端。失败时退化为 KWS 不可用，但不影响转写。

先跑一段时间，确认稳定后再考虑升级到场景 B。

推荐方案

场景 B：KWS + ASR 完整事件流

KWS 切 current_bed，ASR 出正文，状态机把正文归属到当前床号。前端实时展示、人工校对。

通信选 WebSocket，并设计好 partial / final 的 UI 处理。

建议先做场景 A

暂不上场景 B

前端目前不具备处理 partial / final 的能力，强行上场景 B 容易做出不稳定的体验。

先用场景 A 把"切床号"做扎实，等前端工程到位再升级。
